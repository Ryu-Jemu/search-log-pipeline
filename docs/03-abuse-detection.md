# 3단계 · 어뷰징 탐지 규칙과 채점

> 재생기가 **의도적으로 주입한** 어뷰징 캠페인을 ClickHouse SQL 규칙(시간 창 기반)으로 찾고, 정답 라벨과 대조해 채점했습니다.
>
> - **정답 라벨:** `labels_*.json`에만 있고 이벤트에는 없습니다. 라벨은 채점에만 썼습니다.
> - **측정 환경:** Apple M4 · Docker Desktop(CPU 10, 메모리 11.67 GiB, `docs/results/env_mac_m4_resized.json`).
> - **원자료:** `docs/results/abuse_load_mac_m4.json`(적재), `abuse_thresholds_day1_mac_m4.json`(임계값 결정, day1만), `abuse_holdout_mac_m4.json`(보류 데이터 채점), `abuse_hourly_equivalence_mac_m4.json`(운영용 시간 단위 탐지 검증), `abuse_diagnostics_mac_m4.json`(§4의 사후 진단 수치), `fact_checks_mac_m4.json`(DAG 시험 실행).
> - **코드:** `src/slp/abuse.py`(규칙 SQL·채점 함수), `experiments/abuse_score.py`, `dags/abuse_detection.py`, 시험 `tests/test_abuse_rules.py`.

## 1. 데이터와 누수 방지

| 용도 | 재생기 seed | 표 | 유효 이벤트 | 캠페인 |
|---|---|---|---|---|
| 임계값 결정 | 42 (day1) | `events_s42` | 709,950 | 8 |
| 보류 데이터 | 43\~47 (5일) | `events_s43`~`events_s47` | 704,117\~710,966 | 각 8 |

- 각 날짜를 Kafka → 수집기 경로로 적재했습니다. 표마다 행 수, 고유 event_id 수, 재생기 정답의 유효 건수가 같았습니다.
- 가상 날짜(2026-01-05)가 seed마다 같으므로 seed별로 표를 나눴습니다.
- **임계값은 day1만으로 정했습니다.** 결정·채점·운영 확인을 서로 다른 명령으로 실행했습니다.
  - `tune` 단계는 코드상 `events_s42`와 `labels_day1.json`만 읽습니다. 결과 JSON의 `tables_read`는 이 구조를 적어 둔 **고정값**이며, 실제로 읽은 표를 감시하지는 않습니다. 누수 방지는 코드 구조에 기대고 있습니다.
  - `evaluate`는 그 JSON의 임계값을 고정한 채 seed 43\~47에만 적용합니다. `tables_read`가 다르거나 seed 42가 섞이면 멈춥니다(명시적 예외로 검사하므로 `python -O`에서도 동작합니다).
- 보류 데이터를 5일로 잡은 이유: 하루에 캠페인이 3·3·2개뿐이라, 하루로는 유형별 재현율을 0/33/67/100%(distributed_flood는 0/50/100%)로만 낼 수 있습니다. 5일 합계는 query_flood 15개, click_spam 15개, distributed_flood 10개입니다.
- 봇 계정 수(보류 5일): query_flood 15, click_spam 15, distributed_flood 435.

## 2. 규칙
모든 창은 정시에 맞춘 고정 창입니다. 하루를 시간 단위로 나눠 돌려도 결과가 같습니다(§5).

| 규칙 | 단위 · 창 | 통계 | 겨냥한 유형 |
|---|---|---|---|
| R1 버스트 | 사용자 × 5분 | 검색 수 ≥ t, 그리고 서로 다른 쿼리 수 / 검색 수 ≤ d | query_flood, click_spam |
| R2 동일 쿼리 반복 | 사용자 × 1시간 | 검색 수 ≥ m, 그리고 가장 많이 검색한 쿼리의 비율 ≥ s | 세 유형 모두 |
| R3 클릭 스팸 | 사용자 × 1시간 | 같은 문서 클릭 수 최댓값 ≥ c | click_spam |
| R4 쿼리 급증 | 정규화 쿼리 × 10분 구간 | 검색 수 ≥ n, 고유 사용자 ≥ u, z ≥ Z | distributed_flood |

**R4의 z 계산**
- z = (x − λ) / √λ (포아송 근사)입니다.
- λ는 직전 24시간(현재 구간 제외)의 같은 쿼리 검색 수를 144로 나눈 값이고, 하한은 0.1입니다.
- 평소값 계산이 필터 때문에 틀어지지 않는지 시험으로 확인했습니다. 서브쿼리 필터(`n ≥ 5`)가 윈도 함수 안으로 밀려 들어가면 이력 구간이 빠지기 때문입니다.

**식별자는 쓰지 않습니다.** 봇 계정 번호는 정상 사용자 범위(u0000000\~u0099999) 뒤부터 매겨지므로, user_id 값만으로도 봇을 가를 수 있습니다. 실제 서비스에는 없는 단서라 규칙에 쓰지 않았습니다.

## 3. 임계값 결정 (day1만 사용)
**격자**

| 규칙 | 격자 |
|---|---|
| R1 | t ∈ {20 … 120}, d ∈ {1.0(끔), 0.5, 0.2} |
| R2 | m ∈ {3 … 30}, s ∈ {0.5, 0.7, 0.9, 1.0} |
| R3 | c ∈ {2 … 50} |
| R4 | n ∈ {5 … 50}, u ∈ {3 … 30}, Z ∈ {0, 3, 10, 30} |

**선택 기준** (결과 JSON의 `selection` 필드에 기록. 작업 순서상 `tune` 실행 전에 정했지만, 결과와 같은 커밋에 들어 있어 git 이력으로는 보여 줄 수 없습니다.)
- **R1\~R3:** 정밀도와 목표 유형 재현율의 F1이 가장 큰 값을 고릅니다.
  - 정밀도에서는 다른 유형의 봇을 잡아도 정탐으로 셉니다.
  - 같으면 정밀도가 높은 쪽, 그다음 **더 보수적인(엄격한) 임계값**을 고릅니다.
- **R4:** 캠페인 재현율과 탐지 구간 정밀도의 F1이 가장 큰 값을 고르고, 같으면 정밀도가 높은 쪽, 그다음 더 보수적인 값을 고릅니다.

**결정값과 day1 성능**

| 규칙 | 결정값 | day1에서 같은 점수를 낸 설정 수 | day1 성능 |
|---|---|---|---|
| R1 | t=70, d=0.2 | 30개 중 12 | 6계정 탐지, 오탐 0, query_flood 3/3, click_spam 3/3 |
| R2 | m=3, s=1.0 | 36개 중 4 | 94계정, 오탐 0, 단일 봇 6/6, distributed 88/91 |
| R3 | c=50 | 7개 중 6 | 3계정, 오탐 0, click_spam 3/3 |
| R4 | n=50, u=20, Z=30 | 144개 중 120 | 탐지 7건, 오탐 0, 캠페인 2/2 |

day1에서는 만점 구간이 넓었고, 보수적인 쪽을 고르는 규칙 때문에 여러 규칙에서 **격자 끝 값**이 골라졌습니다. R1의 d=0.2, R2의 s=1.0, R3의 c=50, R4의 n=50·Z=30이 그렇습니다. R4의 u=20은 격자 끝이 아닙니다(u=30은 day1에서 캠페인 1/2만 잡아 동률이 아니었음). 이 선택의 영향은 §4-2에 있습니다.

## 4. 보류 데이터 결과 (seed 43\~47, 결정값 고정)
95% 구간은 Clopper-Pearson 정확 신뢰구간입니다.

| 규칙 | 탐지 계정 | 정밀도 (95% 구간) | query_flood | click_spam | distributed_flood |
|---|---|---|---|---|---|
| R1 | 30 | 30/30 (0.884\~1) | 15/15 | 15/15 | 0/435 |
| R2 | 433 | 433/433 (0.992\~1) | 15/15 | 15/15 | **403/435 = 92.6%** (89.8\~94.9%) |
| R3 | 15 | 15/15 (0.782\~1) | 0/15 | 15/15 | 0/435 |
| R1∪R2∪R3 | 433 | 433/433 | 15/15 | 15/15 | 403/435 |
| R1∪R2∪R3∪(R4 구간의 사용자) | 450 | 450/450 (0.992\~1) | 15/15 | 15/15 | **420/435 = 96.6%** (94.4\~98.1%) |

| 규칙 | 캠페인 재현율 | 탐지 구간 | 오탐 구간 |
|---|---|---|---|
| R4 | **8/10** (44.4\~97.5%) | 20 | 0 |

- 보류 5일에서 **결정값 기준 오탐은 모든 규칙에서 0건**이었습니다. 그래서 오탐 표본은 §4-3에서 느슨한 설정으로 살펴봤습니다.
- 표본이 작습니다. 예를 들어 15/15의 95% 하한은 78.2%, 캠페인 8/10의 구간은 44\~97%입니다.
- seed별 값은 원자료 `per_seed`에 있습니다. R4는 seed 45와 46에서 각 1개 캠페인을 놓쳤습니다.

### 4-1. 예상과 다른 점: 계정 단위 규칙(R2)이 distributed_flood를 잡았다
- 인수인계 단계의 예상은 "계정 단위 규칙은 distributed_flood를 놓칠 것"이었습니다. 실제로는 R2가 보류 데이터에서 계정 92.6%를 잡았습니다.
- 이 봇들은 계정마다 3\~8회를 모두 같은 쿼리로 검색합니다. 반면 재생기의 정상 사용자는 같은 쿼리를 거의 반복하지 않습니다.
  - 예: day1 활동 1위 계정은 검색 9,713회 중 서로 다른 쿼리가 9,705개였습니다(검색 기준).
- **해석:** R2의 높은 정밀도는 재생기 가정(쿼리를 인기도 비례로 독립 추출)에서 나온 결과입니다. 실제 사용자는 같은 검색어를 반복하므로(내비게이션 검색, 새로고침 등) 실제 서비스에서는 정밀도가 이보다 낮을 것으로 **추정**합니다. 측정하지는 않았습니다.
- **R2가 놓친 32계정:** 27계정은 총 3회, 5계정은 총 4회 검색했습니다. 모두 검색이 1시간 창 경계에 나뉘어, 어느 창에서도 2회를 넘지 못했습니다. 미끄러지는 창이나 세션 단위 창으로 줄일 수 있을 것으로 보지만, 구현하지 않았습니다.

### 4-2. R4가 놓친 캠페인 2개: 보수적 동률 선택의 대가
| seed · 캠페인 | 계정 | 이벤트 | 길이 | 10분 구간 최대 검색 수 | 구간 최대 고유 사용자 |
|---|---|---|---|---|---|
| 45 · #8 (놓침) | 31 | 159 | 39분 | **41** | 25 |
| 46 · #8 (놓침) | 33 | 164 | 37분 | **49** | 28 |
| 참고: day1 #7 | 34 | 193 | 35분 | 63 | 29 |
| 참고: day1 #8 | 57 | 321 | 38분 | 87 | 47 |

- **원인:** 놓친 두 캠페인은 계정이 적고 오래 이어져, 10분 구간에 몰린 검색이 n=50보다 적었습니다.
  - day1의 두 캠페인(구간 최대 63·87)은 어떤 n에서든 잡혔습니다. 그래서 동률 120개 가운데 가장 엄격한 n=50이 골라졌습니다.
- **사후 확인(표시용, 선택에는 쓰지 않음):** n만 바꾸고 u=20, Z=30을 고정해 보류 데이터에 적용했습니다.

  | n | 캠페인 재현율 | 탐지 구간 | 오탐 |
  |---|---|---|---|
  | 5\~20 | 10/10 | 32 | 0 |
  | 30 | 10/10 | 31 | 0 |
  | 50 | 8/10 | 20 | 0 |

- **교훈:** 만점 구간이 넓을 때 그 끝을 고르면 새 데이터에서 작은 캠페인을 놓칠 수 있습니다. 구간 가운데처럼 여유를 두는 규칙이 더 나았을 것으로 **추정**합니다.
  - 그러나 보류 결과를 본 뒤에 선택 규칙을 바꾸면 누수이므로, 결정값은 그대로 두고 이 결과를 보고합니다.
  - 선택 규칙을 바꾸려면 새 보류 seed로 다시 검증해야 합니다.
- **z 조건의 효과:** day1에서 z 조건(0\~30)은 결과를 바꾸지 않았습니다(동률 120개에 Z 네 값이 모두 포함). 원인은 다음과 같습니다.
  - day1에서 R4 후보 조건(검색 ≥ 5, 고유 사용자 ≥ 3)을 넘은 10분 구간은 9개였고, 모두 캠페인 쿼리였습니다. 캠페인 밖 구간은 하나도 이 조건에 닿지 않아, z로 걸러 낼 대상이 없었습니다.
  - 9개 중 7개는 평소값 λ가 하한(0.1)보다 컸습니다(최대 1.86). 같은 캠페인의 앞 구간이 직전 24시간 이력에 들어가기 때문입니다. 그래도 z 최솟값이 37.5여서 Z ≤ 30 조건은 걸리지 않았습니다.
  - 참고로 day1에 검색된 쿼리의 96.4%(423,041개 중 407,611개)는 하루 1회 이하였습니다.
- **캠페인이 스스로 평소값을 올리는 현상:** 캠페인 뒤쪽 구간일수록 앞 구간이 평소값에 들어가 z가 낮아졌습니다.
  - 예: 보류 seed 46 #7의 13:30 구간은 검색 40건에 z 26.0, seed 47 #8의 17:50 구간은 검색 33건에 z 28.3이었습니다(Z=30 미만).
  - 다만 이 구간들은 건수 조건(n ≥ 50)에서도 빠졌습니다. 이번 데이터에서 n ≥ 50인 캠페인 구간의 z는 모두 37.5 이상이라, z 조건이 결과를 바꾼 경우는 없었습니다.
  - 건수가 큰 긴 캠페인이라면 뒤쪽 구간이 z 때문에 빠질 수 있는 구조라고 **추정**합니다(§6).

### 4-3. 오탐 사례 (느슨한 설정, day1)
결정값에서는 오탐이 없었으므로, 조건을 느슨하게 했을 때 어떤 정상 계정이 걸리는지 day1에서 살펴봤습니다.

**R1을 검색 수만으로 판정할 때(다양성 조건 끔)**

| t | 탐지 | 오탐 | 정밀도 |
|---|---|---|---|
| 40 | 9 | 3 | 0.667 |
| 60\~70 | 7 | 1 | 0.857 |
| 100 이상 | 3 | 0 | 1.0 (대신 단일 봇 재현율 6 → 3) |

오탐된 계정은 활동 순위 1\~3위 정상 사용자였습니다.

| 계정 | 하루 검색 | 서로 다른 쿼리(검색 기준) | 5분 최대 검색 |
|---|---|---|---|
| u0000000 | 9,713 | 9,705 | 93 |
| u0000001 | 5,649 | 5,647 | 54 |
| u0000002 | 3,953 | 3,951 | 48 |

- 재생기의 활동량 가중(순위^-0.8) 때문에 상위 정상 계정의 5분 검색 수가 봇과 겹칩니다. day1 봇의 5분 최대 검색 수는 click_spam 77·78·80회, query_flood 122·125·128회였습니다.
- 이 계정들은 검색 40회 이상인 5분 창에서 다양성 비율(서로 다른 쿼리 / 검색 수)의 최솟값이 1.0이었습니다(`abuse_diagnostics_mac_m4.json`). 반면 5분에 70회 이상 검색한 봇 창 34개의 다양성 비율은 0.0078\~0.0141이었습니다. 그래서 R1에 다양성 조건(≤ 0.2)을 더했습니다. 이 진단 파일은 채점 뒤에 결정 근거를 day1 데이터로 다시 계산해 남긴 **사후 기록**입니다. 결정 당시의 계산 기록은 따로 없습니다.

**R3 c를 낮출 때:** c=2에서 day1 오탐 8, 보류 오탐 52, c=3에서 보류 오탐 1, c≥4에서 0이었습니다.

## 5. 운영: 별도 DAG `abuse_detection`
**지표 DAG와 분리한 이유**
- 실패와 재실행의 단위가 다릅니다. 탐지 임계값을 바꿔 다시 돌려도 지표 버전(v1·v2·v3)이 바뀌지 않습니다.
- 탐지 실패가 지표 확정을 막지 않고, 그 반대도 마찬가지입니다.

**동작**
- 시간 H의 워터마크가 H 끝 + 15분(지표 확정과 같은 조건)을 넘으면 R1\~R4를 평가합니다.
- 결과는 `abuse_detections`(ReplacingMergeTree, 키: 시간·규칙·대상·창)에 씁니다. 같은 시간을 다시 돌리면 병합 전에는 행이 겹칠 수 있지만, `FINAL`로 읽으면(대시보드·실험 모두 그렇게 읽음) 중복이 보이지 않습니다.
- 탐지가 있으면 WARNING 로그 `ABUSE_DETECTED`를 남깁니다.
- 대가: 탐지가 시간 끝 + 15분 뒤에 나옵니다. 실시간 차단 용도가 아니라 사후 집계·정정 용도입니다.

**확인한 것**
- 시간 단위 함수 `detect_hour`를 day1의 25시간에 돌린 합이 하루 단위 결과와 네 규칙 모두 같았습니다(R1 6, R2 94, R3 3, R4 7).
- 임계값 상수(`abuse.CHOSEN`)가 day1 결정 JSON과 같은지도 같은 스크립트에서 확인합니다.
- 컨테이너에서 import 오류가 없었고, `airflow dags test`로 07시 구간을 실행해 성공했습니다(탐지 없음).
  - 처음 시험의 기록은 남기지 않았습니다. 04:49Z에 관측 실행 적재본(같은 day1 데이터)으로 다시 실행한 기록이 `fact_checks_mac_m4.json`에 있습니다("탐지 없음", run state=success).
  - **부작용(검증 중 발견):** `airflow dags test`는 같은 logical date의 기존 run을 지웁니다. logical date 08:00으로 시험하자 예약 run [08:00, 09:00)이 지워지고 수동 run [07:00, 08:00)(`manual__2026-10-15T04:42:05Z`)으로 바뀌었습니다. 지워진 run은 run 개수 변화와 logical date로 **추론**한 것이며, 지워진 run의 목록을 직접 남기지는 않았습니다. 그래서 메타DB의 abuse_detection 예약 run은 관측 실행 직후 12개였다가 11개가 됐습니다(`fact_checks_mac_m4.json`의 note·manual_runs). 운영 DAG에서 `dags test`로 확인하면 실행 기록이 바뀐다는 점에 주의해야 합니다.
  - day1 07시에는 라벨상 캠페인이 없고, 같은 표에 오프라인 `detect_hour`를 돌린 결과도 빈 목록이었습니다(작업 중 확인, 기록 파일 없음).
- 배속 재생 중의 실제 실행은 4단계 관측 실험에서 확인합니다.

## 6. 한계
- **설계 누수:** 규칙을 재생기 코드를 보고 설계했습니다. 보류 데이터는 임계값 과적합만 막아 줄 뿐, 규칙 설계의 누수는 막지 못합니다.
- **재생기의 한계:** 정상 사용자의 반복 검색, 공유 IP, 봇의 위장(다양한 쿼리 섞기, 느린 속도) 같은 행동이 재생기에 없습니다. 이벤트에 IP와 User-Agent도 없습니다. 실제 정밀도·재현율은 이 결과보다 낮을 수 있습니다.
- **표본 크기:** 보류 캠페인 수가 작아 신뢰구간이 넓습니다(distributed 캠페인 10개).
- **R4 평소값:** 하루 이력만 있어 앞부분은 하한값(0.1)을 씁니다. 여러 날 이력이 쌓였을 때의 동작은 시험하지 않았습니다. 또 평소값에서 진행 중인 캠페인 자신을 빼지 않아, 긴 캠페인의 뒤쪽 구간은 z가 낮아집니다(§4-2).
