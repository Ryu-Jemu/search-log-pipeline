# 장애 재현 B · 수집기 강제 종료 → 유실과 중복

> **의도적 장애 주입 실험**입니다.
> - 측정 환경: 2 vCPU · 7.8 GB, Kafka 3.8.0 · ClickHouse 24.8 단일 노드.
> - 입력: `day1.tsv` 전체(유효 709,950건)를 Kafka에 먼저 쌓은 뒤 소비합니다.
> - 정답: 재생기 정답 event_id 집합과 1건 단위로 대조합니다.
>   - 유실 = 정답에는 있는데 표에는 없는 건수
>   - 중복 = 행 수 − 고유 event_id 수
>   - 모든 변형에서 정답에 없는 ID는 0건이었습니다.
> - 원자료: `docs/results/randomkill_*.json`, `failpoint_*.json`, `b_restart_stall.json`, `b_first_run_harness_bug.json`
> - 실행 조건 주의: 결과 JSON은 수집기의 `--resume-from-table` 기본값이 **꺼져 있던** 시점에 만들었다(b4만 명시적으로 켬). 기본값을 켠 뒤에도 같은 조건이 재현되도록 현재 스크립트는 비교 변형에 `--no-resume-from-table`을 붙인다. `duplicate_inserts` 기록은 나중에 추가해서 b0c·b3b 결과에만 있다.
> - 스크립트: `experiments/b_crash.py`, `b_restart.py`

## 1. 가설
- 오프셋을 **적재 전에** 커밋하면, 그 사이에 죽었을 때 데이터가 **유실**된다.
- 오프셋을 **적재 후에** 커밋하면, 적재와 커밋 사이에 죽었을 때 데이터가 **중복**된다.

## 2. 첫 시도에서 드러난 문제 두 가지

### 2-1. 재시작한 수집기가 45초 동안 아무것도 받지 못함
- **증상:** 처음 실험에서는 모든 변형이 576,632~620,147건 "유실"로 집계됐다. 적재 후 커밋 방식도 마찬가지였다. 원자료 JSON은 이후 실행에 덮어써져서, 콘솔 출력값을 `b_first_run_harness_bug.json`에 옮겨 두었다.
- **원인:** `kill -9`로 죽은 소비자가 그룹의 멤버로 계속 남아 있었다. 브로커는 세션 타임아웃(기본 45초)이 지나야 그 멤버를 제거하고 파티션을 다시 배정한다. 재시작한 수집기는 그동안 파티션을 받지 못했고, 5초 유휴 종료 조건에 걸려 그냥 끝났다.
- **측정:** 재시작부터 첫 메시지 수신까지, 3회.

| 설정 | 재시작 → 첫 메시지 |
|---|---|
| 기본(`session.timeout.ms` 45초) | 44.77 / 44.73 / 44.66초 |
| `session.timeout.ms` 6초 | 5.65 / 5.68 / 5.73초 |
| 정적 멤버십(`group.instance.id`) | **0.09 / 0.08 / 0.07초** |

- **조치**
  - 유휴 판정 시각을 수집기 시작이 아니라 **파티션을 배정받은 시점**부터 세도록 고쳤다.
  - 이후 실험은 모두 정적 멤버십으로 진행했다. 같은 ID로 재시작하면 리밸런스 없이 같은 파티션을 즉시 다시 받는다.
- **트레이드오프:** 세션 타임아웃을 짧게 하면 GC나 네트워크 지연만으로도 불필요한 리밸런스가 일어날 수 있다. 그래서 정적 멤버십을 택했다.

### 2-2. 무작위 kill로는 위험한 순간을 거의 맞히지 못함
수집기를 1.5~5초 뒤 무작위로 `kill -9`하기를 변형마다 15회 반복한 결과다.

| 변형 | 유실 | 중복 |
|---|---|---|
| 자동 커밋 | 0 | 152,857 |
| 적재 후 커밋 | **0** | **0** |
| 적재 후 커밋 + 토큰 | 0 | 12,410 |

- "적재 후 커밋"은 중복 0으로 나왔다. 그런데 같은 방식에 (기본 설정에서는 무시되는) 토큰만 붙인 변형에서는 중복이 12,410건 나왔다. 그래서 0은 kill 시점이 우연히 위험 구간을 피한 결과로 **해석**했다. 적재 완료와 커밋 사이 구간이 실제로 얼마나 짧은지는 측정하지 않았다.
- **조치:** 수집기에 **장애 지점 주입**(`--failpoint-prob`, `--failpoint-where`)을 넣었다. 배치마다 정해진 확률로, 정해진 지점에서 스스로 SIGKILL한다. 지점은 ①적재 직전 ②적재 후 커밋 전 두 곳이다.

## 3. 장애 지점 주입 결과

장애 확률은 따로 적지 않았으면 배치마다 0.1이다. b0d는 확률 0.1로 처음 돌렸을 때 장애가 한 번도 나지 않아서 0.3으로 다시 돌렸다.

| 변형 | 장애 횟수 (적재 직전 / 커밋 전) | 유실 | 중복 |
|---|---|---|---|
| b0 자동 커밋, 배치 200ms | 7 (2 / 5) | 0 | 117,858 |
| b0c 자동 커밋, 배치 200ms, 적재 직전만 (확률 0.1) | 10 (10 / 0) | **2,924** | 90,092 |
| b0d 자동 커밋, **배치 2초**, 적재 직전만 (확률 0.3) | 10 (10 / 0) | **76,586** | 0 |
| b0b 자동 커밋, 배치 2초 (확률 0.1) | 1 (0 / 1) | 0 | 18,464 |
| b1 적재 후 커밋 | 12 (6 / 6) | 0 | **62,984** |
| b2 적재 후 커밋 + ReplacingMergeTree | 7 (1 / 6) | 0 | 원본 29,909 → `FINAL` 조회 시 0 |
| b3a 적재 후 커밋 + 중복 제거 토큰(기본 설정) | 6 (4 / 2) | 0 | 19,518 |
| b3b 위와 같음 + `non_replicated_deduplication_window=1000` | 6 (2 / 4) | 0 | 42,594 |
| **b4 적재 후 커밋 + ClickHouse 오프셋으로 재개** (확률 0.3) | **15 (10 / 5)** | **0** | **0** |

### 원인 해석
- **자동 커밋(b0 계열)은 유실과 중복이 둘 다 날 수 있다.** 실제 관측은 다음과 같다.
  - b0c: 유실과 중복이 둘 다 났다.
  - b0d: 유실만 났다.
  - b0·b0b: 중복만 났다. 적재 직전 장애가 2회 이하였다.
  - 원리는 이렇다. librdkafka는 `poll`로 메시지를 넘겨줄 때 오프셋을 저장하고, 이 수집기 설정(`auto.commit.interval.ms` 1000)에 따라 1초마다 백그라운드에서 커밋한다. 커밋 시점이 적재 여부와 무관하므로, 적재 전에 커밋이 지나간 메시지는 **유실**되고 적재 후 아직 커밋되지 않은 메시지는 **중복**된다.
  - 배치 창이 커밋 주기보다 긴 b0d(2초 배치)에서는 적재 직전 장애 10회에 유실이 76,586건 났다. b0c(200ms 배치)는 같은 10회에 2,924건이었다. 다만 두 변형은 장애 확률(0.3과 0.1)도 달랐다. 장애별 유실 건수는 따로 기록하지 않았다.
- **적재 후 커밋(b1)은 유실이 없지만 중복이 생긴다(at-least-once).** 장애 12회(적재 직전 6, 커밋 전 6) 뒤에 중복이 62,984건, 유실이 0건이었다. 원리상 중복은 커밋 전 장애에서 이미 적재된 배치를 다시 읽을 때 생기고, 적재 직전 장애는 커밋 전이라 그대로 다시 읽힌다. 장애별 건수는 따로 기록하지 않았다.
- **중복 제거 토큰(b3)은 기대와 달리 효과가 없었다.**
  - 비복제 MergeTree의 `non_replicated_deduplication_window` 기본값은 **0**이라 토큰이 아예 무시된다(b3a).
  - 창을 켜도(b3b) 같은 배치가 같은 모양으로 다시 들어와야만 중복이 걸러진다. 그런데 실제로 재시작 후 배치의 경계가 달라졌다. 아래는 같은 데이터가 다시 들어간 INSERT 기록이다(`duplicate_inserts`).
    - 처음 INSERT(30.639초): 파티션 0의 74782–78088과 파티션 1의 54502–62874가 한 배치였다.
    - 재시작 후: 파티션 0만 있는 배치(31.160초), 이어서 파티션 1이 54502–59635와 59636–62874 두 배치로 나뉘어 들어왔다.
    - 배치를 시간(200ms)과 poll 순서로 자르기 때문에 경계가 재현되지 않는다. 경계가 다르면 토큰도 달라진다.

## 4. 대안 비교

| 방법 | 정확성 | 비용·제약 |
|---|---|---|
| ① `ReplacingMergeTree(inserted_at)`, 정렬 키에 event_id 포함 | 원본에는 중복이 남고, 병합이 끝나거나 `FINAL`로 읽을 때만 정확 (`FINAL` 709,950 = 정답, `OPTIMIZE FINAL` 뒤 709,950) | 시간별 집계 쿼리 중앙값 10.3ms → `FINAL` 73.0ms(약 7배). 모든 소비 쿼리가 `FINAL`을 기억해야 함 |
| ② 블록 중복 제거 토큰 | 이번 구조에서는 효과 없음 | 배치 경계를 오프셋 기준으로 결정적으로 만들어야 하고, 창 크기 설정도 필요 |
| ③ **ClickHouse에 적재된 오프셋으로 재개** | 15회 장애에서 유실 0·중복 0 | 재시작 시 파티션별 `max(kafka_offset)` 조회 1회. 아래 전제가 필요 |

**③의 원리:** 데이터와 "어디까지 처리했는가"(`kafka_partition`, `kafka_offset` 열)가 **같은 INSERT로 함께 기록**된다. 재시작하면 Kafka 커밋 대신 표에 남은 최대 오프셋+1부터 읽는다. 적재가 됐으면 위치도 같이 기록됐고, 안 됐으면 위치도 없다. 그래서 둘이 어긋날 수 없다.

**③의 전제와 한계 (문서화)**
- **INSERT 하나가 원자적이어야 한다.** 배치가 표의 일별 파티션 두 개에 걸치면 파트별로 따로 기록돼 원자성이 깨질 수 있다. 이번 입력에서도 유효 이벤트 183건(0.03%)의 event_time이 2026-01-06이다. 재생 마지막 구간의 배치는 두 파티션에 걸쳤을 수 있지만, 장애가 바로 그런 INSERT 도중에 났는지는 **확인하지 않았다**. INSERT를 파티션별로 나누는 것만으로는 해결되지 않는다. 나눈 INSERT 사이에서 죽으면, 한쪽에 남은 더 큰 오프셋이 재개 위치가 되어 다른 쪽이 유실될 수 있다. 대응 방안(예: 재개 위치를 보수적으로 잡고, 그로 인한 중복은 ①로 흡수)은 아직 구현·시험하지 않았다.
- **Kafka 파티션 하나에 쓰는 프로세스가 하나뿐이어야 한다.** 정적 멤버십과 SIGKILL 환경에서 확인했다. 좀비 프로세스가 계속 쓰는 상황은 시험하지 않았다.
- **DLQ는 여전히 at-least-once다.** 장애가 나면 DLQ 메시지가 다시 전송돼 정답 390건보다 많았다(b4는 435건). DLQ를 읽는 쪽에서 `src` 헤더(파티션:오프셋)로 중복을 걸러야 한다.

## 5. 채택
- 수집기 기본값: **적재 후 커밋 + ClickHouse 오프셋으로 재개**(`--resume-from-table`이 기본, `--no-resume-from-table`로 끌 수 있음) + **정적 멤버십**(`--instance-id`)
- Kafka 커밋은 lag 모니터링 용도로 유지한다.
- ①은 이후 다른 경로(예: 재처리 백필)로 같은 이벤트가 들어올 때를 대비한 2차 방어선으로 검토한다.

## 6. 재발 방지
- `experiments/b_crash.py --mode failpoint`로 변형별 유실·중복을 정답과 대조한다. 수집기를 바꿀 때마다 다시 돌릴 수 있다.
- 비교용 변형은 `--no-resume-from-table`을 명시해 기본값이 바뀌어도 같은 조건이 재현되게 했다.
